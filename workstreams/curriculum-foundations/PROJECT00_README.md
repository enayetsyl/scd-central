## 1. Purpose & Scope

A multi-month effort to systematically raise teaching quality across an Islamic primary school. The immediate goal is to establish the operational backbone (8 Projects, governance documents, conventions) after which content production (lesson plans, question banks, replacement content) proceeds across **all classes (C1–C5) and all subjects**, sequenced at the Principal's discretion and paced by upstream readiness per the D-005 build chain. *Scope change (D-046, 2026-05-27 — supersedes D-001/D-038/D-040): the single-slice **Class 1 Bangla, পাঠ 1–16** pilot is **retired** as the gating deliverable. Lifting the cap changes what may be selected next, not the per-division preparation each item still requires — the D-005 build order, the D-045 annotated-skeleton lock-gate, and the D-042 TG-reconciliation gate all still apply per class × subject, so the true production frontier is upstream readiness, not this decision.*

The long-term goal is that every class and subject has: (a) Bloom's-aligned reviewable lesson plans, (b) substantial chapter/topic-wise question banks, (c) Islamic-aligned replacement content where NCTB conflicts with our values, (d) live trackers with follow-up automation, (e) ongoing teacher training and observation.

## 2. Strategic Context

**The 11 problems being addressed:**

1. Teacher quality varies; most are not highly qualified or trained.
2. Most teachers cannot independently produce a strong lesson plan.
3. Most teachers struggle to set questions at appropriate difficulty.
4. Most teachers struggle to check exam scripts properly.
5. Most teachers have weak classroom management.
6. Homework/assignment non-submission is rarely followed up.
7. Lesson plan, question paper, and homework do not always align.
8. NCTB books change yearly, forcing repeated lesson-plan rework.
9. NCTB content sometimes contradicts Islamic values.
10. Old fully-scripted senior-teacher lesson plans removed dynamism; loose plans erode standards.
11. (Internal) No reviewable framework exists to evaluate classes, questions, or assignments against a single rubric.

**The 9-part response plan:**

1. 10-year NCTB stability analysis per (class, subject) — identify what is constant.
2. Bloom's Taxonomy as the universal framework.
3. Three-layer lesson plans (Spine / Suggested Flow / Flex Zone) for every chapter, all subjects.
4. Chapter and topic-wise question banks, substantial volume for weak-student practice.
5. Comprehensive trackers (homework, Quran, assignment, class test, vocabulary, complaint, lesson completion).
6. Master tracker — aggregates all data for principal-level analysis (student / class / subject / teacher-wise).
7. Teacher training based on Bloom's (V1A comprehensive primer already exists; V1B and V1C to be derived).
8. Principal dashboards for ongoing monitoring.
9. Class, question, and assignment review framework.

### 5.3 Draft vs Locked

- `DRAFT_*` prefix or `/drafts/` folder for in-progress work.
- `LOCKED_*` prefix or `/locked/` folder for approved-and-canonical versions.
- Locked outputs are never edited in place; superseded only by a newer locked version (old one archived).
- Standing instruction in every Project: ask before overwriting a LOCKED file.
- **Pre-supersede dependent check (D-PROJ00-061).** Before superseding any LOCKED reference, consult `PROJECT00_CROSS_PROJECT_INDEX.md` for that reference's downstream dependents — **including built assets** (a standing file that carries an extracted copy of the reference's payload, e.g. the Project 03 Production Core). For each dependent, flag the refresh or rebuild owed per §5.4 before the supersede is treated as complete. A reference supersede is not finished until its owed rebuilds are flagged.

### 5.4 Cross-Project propagation

Standing instruction in every Project's Instructions: when a fact, decision, or change in this chat could affect another Project or a standing rule, **pause and flag it** — state which Project(s) are affected, draft the exact text needed, ask whether to apply now or add to TODO.

**Supersede-dependent rule (general — D-PROJ00-061).** Some references are *assembled into* a downstream **built asset** that carries an extracted copy of their payload (not just consumed in place). When such a reference is superseded, the built asset is **stale** and must be **rebuilt from the new source** before it is used again. The dependency map is `PROJECT00_CROSS_PROJECT_INDEX.md`: any reference whose consumer rows name a built asset is in scope. At supersede time, Claude consults the index, names every owed rebuild, and routes it through this section (apply now or add to that Project's TODO) — the same way a consuming Project would be flagged. The rule scales: when a future reference→asset dependency is created, it is recorded once in the index and this rule covers it without amendment here. **Payload scope:** the trigger is a change to the **extracted payload** (the asset's copied content), not any edit whatsoever — a payload-neutral edit to a source reference (e.g. adding the back-pointer footer that records this very dependency) supersedes the file but does **not**, by itself, make the asset stale.

> **Worked example — the Project 03 Production Core.** `LOCKED_ProductionCore_v1` is built from four school-wide content REFs: **REF-02** (Core §1–§3) · **REF-07** (§4 revision rule) · **REF-08** (§5 homework rule) · **REF-18 V1C** (§6 Bloom pocket). A supersede of *any one* of these makes the Core stale → **rebuild required** before any new Chapter/Session Plan is built off it. This is enforced on three layers: **(1) change-time** — the §5.3 pre-supersede check + this rule fire when the REF is superseded *here* in Project 00; **(2) the index** records the dependency (REF-02/07/08/18 consumer rows) so it is auditable; **(3) consume-time** — the Core's own §0 stamp check + §7 rebuild trigger, governed by `LOCKED_ProductionAsset_Build_Policy_v1` §6 (Project 03), catch any stale Core when a production chat loads it. Layers 1–2 live in Project 00; layer 3 already exists in Project 03. The Production Pack(s) carry **no** Core payload and are unaffected by a Core rebuild.

### 5.5 Handoff at end of substantial chats

Any chat that produced meaningful work ends with a handoff document `PROJECT{NN}_handoff_YYYY-MM-DD_topic.md` saved in /handoffs/. Two tiers based on chat scope:

**Light handoff (~30 lines) — default.** Use when:
- The chat produced one or two artifacts and made no decisions affecting other Projects.
- All changes are scoped within one Project.
- No locked file was modified or superseded.

Required content:
- One-line chat summary.
- Accomplishments (3–6 bullets).
- Decisions made (filename and decision ID if logged).
- Output file locations.
- Exact starter prompt for the next chat (one paragraph).

**Full handoff (~80 lines) — triggered when any of these is true:**
- A decision was made that affects another Project (§5.4 propagation flag).
- A locked file was modified, superseded, or archived.
- A new standing convention was added or amended.
- The chat produced more than two artifacts, or work spans multiple class×subjects.
- A `MANIFEST_archived_files.md` row was added or revised (§4.13).

Full handoff content adds, beyond the light handoff:
- Cross-Project propagation patches (drafted, marked "to apply") with target files and version bumps.
- Open items and dependencies.
- Manifest updates (new rows or revisions, full text).
- Any borderline rulings, edge cases logged for REF-01 §4.5, or decision-review requests.

**Light vs Full is Claude's call by default**, based on the trigger list. If the trigger is borderline, Claude proposes Light and notes what would be added if upgraded; the Principal confirms or upgrades.

**Trivial chats** — pure clarification, single Q&A, no artifacts produced — get no handoff. The §4.6 long-chat rule still applies independently for context-overload protection.

### 5.10 Chat-naming convention

Standing instruction (D-044): because Projects 03–05 will each spawn many chats (one skeleton chat per class × subject, one lesson-plan chat per class × subject × division — potentially hundreds), every chat is given a structured title so each Project's chat list stays sortable and any single chat is identifiable at a glance.

- **`{scope}`** — the subject anchor. For class × subject work: `C{class} {SUBJECT}` using the D-019 subject codes (e.g. `C1 BAN`). For non-content work: a short reference or topic token (e.g. `REF-20`, `Curation`, `Index`).

- **`· v{n}`** — optional; only for a redo or continuation of an earlier chat on the same unit.

### 5.11 Element-level curation scan (annotated-skeleton lock-gate)

Standing instruction (D-045): an annotated skeleton — and any content authored against the Curation Policy — is built from an **exhaustive element-level scan of the actual target-edition textbook** (every title, example word, practice/exercise/counting item, and illustration), never from the stability skeleton, the Teacher Guide, or sample pages. The scan runs a **separate illustration pass**, greps every element against **REF-21 (Curation Trigger Lexicon & Skeleton Scan Protocol)**, records a **per-division scan ledger with a completeness assertion** (spot-checking or inferring "formulaic" divisions is prohibited), and compiles a **Borderline / Escalation register** for Principal ruling. The annotated skeleton may not lock — and may not feed Project 05 — until the ledger, the illustration pass, and the Principal's borderline ruling are complete. Build a subject-specific lexicon extension first (REF-21 §4); every borderline ruling feeds back as a REF-01 §4.5 edge case.

### 5.12 Archived files manifest discipline

Each Project that uses the local-machine archive pattern holds a `MANIFEST_archived_files.md` in its Project knowledge, listing files moved to the Principal's local machine. The manifest is the canonical index of what exists, where it is, and when to ask for it back.

**Claude's responsibilities at the start of any task:**

1. Consult the manifest (via `project_knowledge_search` with a targeted query, or `view` if specific filename(s) known).
2. Match the task against each row's "Upload when" trigger.
3. If a trigger matches, **stop before proceeding** and tell the Principal: *"This task likely needs `[filename]` per the manifest. Could you upload it?"* — naming the file and the matching trigger. Multiple required files are listed in one message, not piecemeal.

**What Claude does NOT do:**

- Does **not** infer file contents from filename alone.
- Does **not** proceed on the assumption that the missing file would say X.
- Does **not** silently work around the gap.

### 5.13 Tool-use discipline

Standing rules for Claude's use of file-reading and file-editing tools in any chat. These rules trim wasted re-streaming and prevent the patterns the 2026-05-27 token-usage analysis identified.

**File-viewing rules:**

- **No re-pagination after a full-file view.** If Claude has run `view` on a file without `view_range`, the entire file is already in context. Do not subsequently `view` ranges of the same file in the same chat — re-read from context instead.
- **No overlapping `view_range` calls.** If Claude has viewed lines 1–200, do not subsequently view 150–250 in the same chat — view 201–250 instead, or re-read from context.
- **Prefer `project_knowledge_search` over `view` for reference lookups.** When the question is "what does C-07 say" or "what's the REF-19 entry for C3 Bangla," use targeted search rather than full-file view. Reserve `view` for files being patched in this chat, or where the search snippet is insufficient.

**Bash discipline:**

- **Combine diagnostic commands.** One `wc -l + ls + file` invocation instead of three separate ones. One `cat A B C` instead of three `cat` calls. Multi-step diagnostics chain with `&&` or `;` in a single tool call.

**File-editing rules:**

- **Default to patch over regeneration for files >100 lines.** Use `str_replace` or diff-style patches. Full regeneration of a file is acceptable only when (a) the file is ≤100 lines, or (b) the change spans more than ~30% of the file.
- **Patches name the target file, the anchor text, and the replacement clearly.** No ambiguous "update the table" — quote the row.
- **One file's patches are presented as a block.** Don't interleave patches across multiple files; finish one file's patch set before starting another's, so the Principal can apply them sequentially.

**Project file discipline:**

- **Do not re-read files already in Project knowledge.** They load automatically into chat context. Re-uploading a Project file or `view`-ing it from a re-upload path is double-loading.
- **If a Project file appears in `/mnt/project/`, reference it from there.** Do not re-upload during the chat.

### 5.14 Cross-Project consult-routine (cross-cutting work)

Standing instruction (D-048) — an **extension of §5.8, not a replacement.** §5.8 covers the normal case: at the start of any chat, read *this* Project's README and TODO. §5.14 covers **cross-cutting work** — any task whose changes are expected to land in more than one Project. In that case, before producing anything, also consult the README and TODO of each other Project the task is expected to touch.

**A task is cross-cutting when any of these is true:**

- It amends a master §5 convention or a master decision (every Project's Instructions echo these).
- It produces or supersedes a LOCKED REF that more than one Project consumes (per CROSS_PROJECT_INDEX).
- A §5.4 propagation flag is expected to fire into one or more named Projects.
- It moves, renames, or archives files held in more than one Project.

**At task start (in addition to §5.8):**

1. Identify the touched Projects — from the request, from CROSS_PROJECT_INDEX, and from the §5.4 propagation expectation.
2. For each touched Project, read the **relevant sections** of its README and TODO (not the whole files) — its inherited-conventions area, its open-items/TODO, and any version line that would change. Use `project_knowledge_search` with a targeted query, or `view` on a known section range, per §5.13.
3. Note any conflict, stale cross-reference, or already-applied change in the touched Projects **before drafting**, so each propagation patch matches the live state rather than an assumed one.
4. Draft each Project's patch against what was actually read, mark it "to apply," and route it through §5.4 (apply now or add to that Project's TODO).

**Scope guard:** §5.14 is a *read-before-you-touch* rule, not a license to edit other Projects' files in this chat. Cross-Project edits still follow §5.3 (ask before overwriting LOCKED) and the file-upload workflow (Principal uploads the target file; Claude returns the updated file). Reading stays targeted — whole-file reads of every Project are exactly the token cost §5.13 exists to prevent.

## 6. Build Dependency Order

The non-negotiable order of construction (D-005):

```
Stability Analysis (per class+subject)
    ↓
Annotated Skeleton (Curation Policy applied)
    ↓
Replacement Content (for lessons flagged NEEDS-REPLACEMENT)
    ↓
Lesson Plans (three-layer)
    ↓
Question Banks (per topic, Bloom's-tagged)
```

Trackers and teacher training run in parallel to content production, not in this critical path.

The **Vertical Topic Progression Map (REF-19, D-039)** is also a parallel layer, but *downstream*: it aggregates completed stability skeletons across a subject's classes to inform per-year emphasis. It does **not** re-order the chain above — it feeds the Subject Spine Playbooks (REF-03) and, through them, lesson-plan emphasis decisions, only after a subject's class-stack of analyses exists.

**Teacher-Guide (TG) Reconciliation (D-042)** is a mandatory **validation gate** inside this chain (not a parallel layer): for each class × subject the NCTB Teacher Guide — which carries the per-lesson যোগ্যতা/শিখনফল the textbook omits — is reconciled against the completed skeleton (producing the fourth REF-05 artifact) **before lesson-plan production begins**, so Projects 03/04/05 build on TG-validated per-lesson objectives. It refines, not re-orders, the chain above. Method: REF-04 §16.
