## How to use this index

**When updating a canonical reference in Project 00:** consult the [forward view](#forward-view--references--consuming-projects) to see which consuming Projects need a refresh. Per PROJECT00_README.md §5.4 (cross-Project propagation), flag each affected Project before applying the change.

**Downstream dependents include built assets, not just Projects.** Some references are *assembled into* a standing build asset that carries an extracted copy of their payload — most notably the **Project 03 Production Core** (`LOCKED_ProductionCore_v3`), built from **REF-02 / REF-07 / REF-08 / REF-18**. A supersede of any such source reference makes the asset **stale → rebuild required** before it is used again. When superseding a reference, check its consumer rows for any built asset and flag every rebuild owed (README §5.3 pre-supersede check / §5.4 propagation). This index is the single lookup for those dependencies.

**When starting work in any Project 01–08:** consult the [reverse view](#reverse-view--project--references-it-needs) to see which Project 00 references should be loaded into context first. Several Projects depend on multiple Project 00 documents — load them all.

**When producing a new canonical reference in Project 00:** add a new row to the forward view, populate consuming Projects, and update the reverse view accordingly. Log the addition in §"Version log".

## Update protocol

This index is **append-and-amend**, not append-only. The reference list is expected to grow and statuses to change as the initiative progresses.

### When a reference becomes locked or updated

1. Update the **Status** row of the affected REF entry in the forward view.
2. Check the consuming-Projects column. For each Project listed:
   - Per PROJECT00_README.md §5.4 (cross-Project propagation), flag the change.
   - Determine whether the consuming Project needs to refresh its working files, retrain teachers, or merely note the change.
3. Add an entry to the consuming Project's `PROJECT{NN}_DECISIONS.md` noting that they have absorbed the updated reference.
4. Log the update in §"Version log" of this file.

### When a new canonical reference is produced

1. Assign the next REF number (REF-27, ...).
2. Add a forward-view section with consuming Projects and status.
3. Update each affected Project's reverse-view section.
4. Log in §"Version log".

### When a reference is deprecated

1. Mark status as `DEPRECATED — see [Replacement]`.
2. Keep the entry for at least 60 days for chat-trail interpretability (same convention as PROJECT00_GLOSSARY.md).
3. Flag affected Projects via cross-Project propagation.
